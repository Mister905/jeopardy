# Supabase Auth Integration Plan

## Description

Implement authentication infrastructure using Supabase Auth in the NestJS backend. This includes initializing Supabase Auth, JWT verification, authentication guards/middleware, and passing authenticated user context to domain services. This supports Phase 5 of the implementation roadmap. This plan focuses on backend architecture and responsibilities only - no frontend or UI auth flows are included.

## Files to Create

- `backend/src/auth/supabase.service.ts` - Supabase client initialization and configuration service
- `backend/src/auth/supabase.service.spec.ts` - Unit tests for Supabase service
- `backend/src/auth/auth.guard.ts` - Authentication guard for protecting routes
- `backend/src/auth/auth.guard.spec.ts` - Unit tests for auth guard
- `backend/src/auth/decorators/current-user.decorator.ts` - Custom decorator to extract authenticated user from request
- `backend/src/auth/types.ts` - TypeScript interfaces for authenticated user context
- `backend/src/auth/auth.module.ts` - NestJS module for auth infrastructure
- `backend/src/auth/index.ts` - Export barrel file

## Files to Modify

- `backend/src/app.module.ts` - Register AuthModule
- `backend/src/main.ts` - Add global authentication guard if needed (optional, can be per-route)

## Architecture

### Supabase Auth Initialization

#### Responsibility: SupabaseService
- Initialize Supabase client using project URL and anon key from environment variables
- Configure JWT verification settings (JWT secret for token verification)
- Provide methods to verify JWT tokens using Supabase's verification logic
- Handle Supabase client lifecycle (initialization, cleanup if needed)

#### Configuration
- Read `SUPABASE_URL` from environment variables
- Read `SUPABASE_ANON_KEY` from environment variables
- Read `SUPABASE_JWT_SECRET` from environment variables (for backend JWT verification)
- All configuration accessed via ConfigService (consistent with PrismaService pattern)

#### Service Structure
- Injectable service following NestJS patterns
- Exposes Supabase client instance for token verification
- Provides `verifyToken(token: string)` method that returns verified user payload
- Handles Supabase-specific errors and maps to application errors

### JWT Verification

#### Responsibility: AuthGuard
- Intercept HTTP requests to protected endpoints
- Extract JWT token from Authorization header (Bearer token format)
- Verify token using SupabaseService
- Attach authenticated user context to request object
- Reject requests with invalid or missing tokens

#### Verification Flow
1. Guard checks if route requires authentication (via decorator or metadata)
2. Extract token from `Authorization: Bearer <token>` header
3. If token missing: throw UnauthorizedException (401)
4. Call SupabaseService.verifyToken() to verify JWT
5. If verification fails: throw UnauthorizedException (401)
6. If verification succeeds: extract user payload and attach to request
7. Allow request to proceed to controller

#### Guard Implementation
- Extends NestJS `CanActivate` interface
- Can be applied globally, per-controller, or per-route using `@UseGuards()`
- Uses ExecutionContext to access request object
- Attaches verified user data to request for downstream use

### UserId Extraction from JWT Claims

#### Responsibility: CurrentUser Decorator
- Custom parameter decorator to extract authenticated user from request
- Reads user data attached by AuthGuard
- Provides type-safe access to userId and other user claims
- Can be used in controller methods: `@CurrentUser() user: AuthenticatedUser`

#### JWT Claims Structure
- Supabase JWT contains `sub` claim (user ID/UUID)
- May contain additional claims: `email`, `role`, etc.
- Extract `sub` as primary userId for domain entity association
- Map Supabase JWT structure to application's AuthenticatedUser type

#### User Context Type
- Define `AuthenticatedUser` interface with:
  - `userId: string` (from JWT `sub` claim)
  - `email?: string` (if available in JWT)
  - Other relevant claims as needed

### Authentication Guard/Middleware Structure

#### Guard Application Strategy
- **Per-route**: Use `@UseGuards(AuthGuard)` on specific controller methods
- **Per-controller**: Use `@UseGuards(AuthGuard)` on controller class
- **Global**: Apply globally in main.ts (optional, can be selective)
- **Public routes**: Use `@Public()` decorator to bypass authentication for specific routes

#### Guard Responsibilities
- Token extraction and validation
- User context attachment
- Error handling (401 Unauthorized for invalid/missing tokens)
- No business logic - purely authentication concern

#### Middleware vs Guard
- Use NestJS Guards (not Express middleware) for consistency with NestJS patterns
- Guards integrate with NestJS dependency injection
- Guards can access ExecutionContext for request/response manipulation

### Authenticated User Context to Domain Services

#### Responsibility: Controllers
- Extract userId using `@CurrentUser()` decorator
- Pass userId explicitly to domain service methods
- No implicit user context - always explicit parameter passing

#### Responsibility: Domain Services
- Accept userId as explicit parameter in method signatures
- Use userId for entity creation, queries, and authorization checks
- No dependency on request object or authentication infrastructure
- Services remain pure and testable

#### Context Flow
1. Request arrives with JWT token
2. AuthGuard verifies token and attaches user to request
3. Controller method uses `@CurrentUser()` decorator to get userId
4. Controller calls domain service method with userId parameter
5. Domain service uses userId for business logic (create game, query games, etc.)

#### Example Pattern
```typescript
// Controller
@Post('games')
@UseGuards(AuthGuard)
createGame(@CurrentUser() user: AuthenticatedUser) {
  return this.gameService.createGame(user.userId);
}

// Service
async createGame(userId: string): Promise<CreateGameResult> {
  // Use userId for game creation
}
```

## Data Structure

### Environment Variables
- `SUPABASE_URL`: Supabase project URL
- `SUPABASE_ANON_KEY`: Supabase anonymous/public key
- `SUPABASE_JWT_SECRET`: JWT secret for backend token verification

### AuthenticatedUser Interface
```typescript
interface AuthenticatedUser {
  userId: string; // From JWT 'sub' claim
  email?: string; // From JWT if available
}
```

### JWT Token Format
- Header: `Authorization: Bearer <jwt_token>`
- Token structure: Standard JWT with Supabase claims
- Primary claim: `sub` (user ID/UUID)

## Algorithm

### Step 1: Supabase Client Initialization
1. SupabaseService constructor receives ConfigService
2. Read SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_JWT_SECRET from environment
3. Initialize Supabase client with URL and anon key
4. Store JWT secret for token verification
5. Service is ready for token verification

### Step 2: Request Interception (AuthGuard)
1. Guard checks if route requires authentication
2. Extract Authorization header from request
3. Parse Bearer token from header value
4. If token missing: throw UnauthorizedException (401)
5. Call SupabaseService.verifyToken(token)
6. If verification fails: throw UnauthorizedException (401)
7. Extract user payload from verified token
8. Attach AuthenticatedUser to request object
9. Allow request to proceed

### Step 3: User Context Extraction (Controller)
1. Controller method receives request
2. Use @CurrentUser() decorator on parameter
3. Decorator reads AuthenticatedUser from request (attached by guard)
4. Controller now has access to userId
5. Pass userId to domain service method

### Step 4: Domain Service Usage
1. Domain service method receives userId as parameter
2. Service uses userId for:
   - Entity creation (associate with user)
   - Query filtering (only user's entities)
   - Authorization checks (verify ownership)
3. No dependency on authentication infrastructure

## Error Handling

### Authentication Errors
- Missing token: 401 Unauthorized
- Invalid token: 401 Unauthorized
- Expired token: 401 Unauthorized
- Malformed token: 401 Unauthorized
- Supabase verification failure: 401 Unauthorized

### Configuration Errors
- Missing SUPABASE_URL: Throw error on service initialization
- Missing SUPABASE_ANON_KEY: Throw error on service initialization
- Missing SUPABASE_JWT_SECRET: Throw error on service initialization

### Error Response Format
- Use NestJS built-in exception handling
- UnauthorizedException returns standard 401 response
- Error messages should not expose internal details

## Constraints

- **Backend only**: No frontend authentication flows, no UI components
- **Explicit userId passing**: Domain services receive userId as parameter, no implicit context
- **No business logic in guards**: Guards only handle authentication, not authorization rules
- **Service independence**: Domain services have no dependency on auth infrastructure
- **Type safety**: Use TypeScript interfaces for authenticated user context
- **NestJS patterns**: Follow existing codebase patterns (similar to PrismaModule structure)

## What is NOT Handled

- **Frontend authentication**: No login/registration UI, no frontend token management
- **User registration/login endpoints**: Backend auth infrastructure only, not auth flows
- **Password management**: Handled by Supabase, not implemented in backend
- **Token refresh**: Handled by Supabase client, not implemented in backend
- **Session management**: Handled by Supabase, backend only verifies tokens
- **User profile management**: Not part of authentication infrastructure
- **OAuth providers**: Not included in initial implementation

## Testing Strategy

### Unit Tests

1. **SupabaseService**
   - Test client initialization with valid config
   - Test client initialization with missing config (throws error)
   - Test verifyToken() with valid token (returns user)
   - Test verifyToken() with invalid token (throws error)
   - Test verifyToken() with expired token (throws error)

2. **AuthGuard**
   - Test token extraction from Authorization header
   - Test missing token (throws UnauthorizedException)
   - Test invalid token (throws UnauthorizedException)
   - Test valid token (attaches user to request, allows request)
   - Test guard with @Public() decorator (bypasses authentication)

3. **CurrentUser Decorator**
   - Test extraction of user from request
   - Test with missing user (throws error)
   - Test type safety

### Integration Tests

1. **End-to-End Authentication Flow**
   - Request with valid Supabase JWT token
   - Verify guard extracts and validates token
   - Verify user context available in controller
   - Verify userId passed to domain service

2. **Error Scenarios**
   - Request without token (401)
   - Request with invalid token (401)
   - Request with expired token (401)

## Exit Conditions

The authentication infrastructure is complete when:
- Supabase Auth is initialized in backend with proper configuration
- JWT verification works for all protected endpoints
- AuthGuard can extract and verify Supabase JWT tokens
- UserId can be reliably extracted from JWT claims using @CurrentUser() decorator
- Authenticated user context is passed to domain services via explicit userId parameter
- All protected endpoints require valid authentication
- Unit tests cover authentication flow and error scenarios
- Integration tests verify end-to-end authentication
- Domain services can receive and use userId for entity association and authorization

The system is ready for Phase 6 (API Contracts & Endpoints) when:
- API endpoints can use @UseGuards(AuthGuard) to protect routes
- Controllers can extract userId using @CurrentUser() decorator
- Domain services receive userId and associate entities correctly
- Authorization checks can verify user ownership of resources
