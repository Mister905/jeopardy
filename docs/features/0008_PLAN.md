# Phase 7: Frontend Skeleton - Implementation Plan

## Description

Build a minimal frontend application shell using Next.js (React) that integrates with the existing backend API endpoints. The frontend will render backend state only, with no client-side business logic or rule enforcement. All game state, scoring, and validation remain authoritative on the backend. This supports Phase 7 of the implementation roadmap.

## Page/Route Structure

### 1. `/` (Home/Landing Page)

**Purpose**: Entry point, redirects to login if not authenticated, or to games list if authenticated.

**Authentication**: 
- Public route
- Redirects to `/auth/login` if not authenticated
- Redirects to `/games` if authenticated

**Data Fetched**: None (redirect only)

**API Endpoints Consumed**: None

**UI Responsibilities**:
- Check authentication status
- Redirect appropriately
- Display loading state during auth check

**Backend Responsibilities**: N/A (client-side redirect only)

---

### 2. `/auth/login` (Login Page)

**Purpose**: Authenticate user via Supabase Auth.

**Authentication**: Public route (unauthenticated users only)

**Data Fetched**: None (Supabase handles auth flow)

**API Endpoints Consumed**: None (Supabase Auth SDK handles authentication)

**UI Responsibilities**:
- Display login form/button
- Initiate Supabase authentication flow
- Handle authentication errors
- Redirect to `/games` on successful login

**Backend Responsibilities**: N/A (Supabase Auth handles authentication)

**Authentication Flow**:
1. User clicks login button
2. Redirect to Supabase Auth (or show Supabase Auth UI)
3. User authenticates with Supabase
4. Supabase redirects to `/auth/callback` with auth code
5. Frontend exchanges code for session
6. Store JWT token (Supabase handles this)
7. Redirect to `/games`

---

### 3. `/auth/callback` (Auth Callback Handler)

**Purpose**: Handle Supabase authentication callback and establish session.

**Authentication**: Public route

**Data Fetched**: None

**API Endpoints Consumed**: None (Supabase SDK handles token exchange)

**UI Responsibilities**:
- Extract auth code from URL
- Exchange code for session via Supabase SDK
- Store session/token
- Redirect to `/games` on success
- Display error and redirect to `/auth/login` on failure

**Backend Responsibilities**: N/A

---

### 4. `/games` (Game List Page)

**Purpose**: Display list of user's games (active and completed).

**Authentication**: Protected route (requires valid JWT)

**Data Fetched**: 
- List of user's games
- Game metadata (id, state, score, createdAt, updatedAt)

**API Endpoints Consumed**:
- `GET /games` - Fetch user's games
  - Query params: `status` (optional), `limit` (optional), `offset` (optional)

**Request Headers**:
- `Authorization: Bearer <jwt-token>` (required)

**Response Data Structure**:
```typescript
{
  games: Array<{
    id: string;
    userId: string;
    state: 'PENDING' | 'ACTIVE' | 'FINAL_PENDING' | 'FINAL_ACTIVE' | 'ELIMINATED' | 'COMPLETED';
    score: number;
    createdAt: string;
    updatedAt: string;
  }>;
  total: number;
  limit: number;
  offset: number;
}
```

**UI Responsibilities**:
- Display list of games
- Show game state (PENDING, ACTIVE, COMPLETED, etc.)
- Show final score for completed games
- Show "New Game" button (creates new game)
- Link to individual game pages
- Handle loading states
- Handle error states (401, 403, 500)
- Display empty state if no games exist

**Backend Responsibilities**:
- Authenticate user via JWT
- Return only user's own games
- Filter by status if query param provided
- Paginate results

**State-Driven UI**:
- "New Game" button: Always enabled (backend enforces one active game rule)
- Game cards: Show different styling based on `state`
  - PENDING: "Not Started" badge
  - ACTIVE: "In Progress" badge with current score
  - FINAL_PENDING: "Final Jeopardy" badge
  - FINAL_ACTIVE: "Final Jeopardy" badge
  - COMPLETED: "Completed" badge with final score
  - ELIMINATED: "Eliminated" badge

---

### 5. `/games/[id]` (Game Detail/Play Page)

**Purpose**: Display game details and allow gameplay interactions.

**Authentication**: Protected route (requires valid JWT)

**Data Fetched**:
- Game details (full game object with clues)
- Current board state (if game is active)

**API Endpoints Consumed**:
- `GET /games/:id` - Fetch game details
- `GET /games/:id/board` - Fetch current board state (if game is ACTIVE)
- `POST /games/:id/start` - Start game (if state is PENDING)
- `POST /games/:id/clues/:clueId/wager` - Submit Daily Double wager
- `POST /games/:id/clues/:clueId/answer` - Answer a clue
- `POST /games/:id/final-jeopardy/wager` - Submit Final Jeopardy wager
- `POST /games/:id/final-jeopardy/answer` - Answer Final Jeopardy

**Request Headers**:
- `Authorization: Bearer <jwt-token>` (required for all requests)

**UI Responsibilities**:
- Display game state and score
- Render appropriate view based on game state:
  - **PENDING**: Show "Start Game" button, display Final Jeopardy category (if available)
  - **ACTIVE**: Show game board (Jeopardy or Double Jeopardy), allow clue selection
  - **FINAL_PENDING**: Show Final Jeopardy category, wager input form
  - **FINAL_ACTIVE**: Show Final Jeopardy question, answer adjudication buttons
  - **COMPLETED**: Show final results, read-only view
  - **ELIMINATED**: Show elimination message, read-only view
- Handle user interactions:
  - Click clue → Show clue question/answer (if resolved) or allow answering (if unanswered)
  - Submit wager → Send to backend, update UI with response
  - Submit answer → Send to backend, update UI with response
- Refresh game state after each action
- Display loading states during API calls
- Display error messages from API responses
- Disable interactions for completed/eliminated games

**Backend Responsibilities**:
- Authenticate and authorize (user owns game)
- Validate game state before actions
- Enforce business rules (wager bounds, state transitions, etc.)
- Calculate and persist score changes
- Return updated game state after actions

**State-Driven UI Examples**:
- **PENDING state**:
  - Show: "Start Game" button
  - Hide: Game board, clue interactions
  - Display: Final Jeopardy category (from `game.finalJeopardy.clue.category`)
- **ACTIVE state**:
  - Show: Game board with clues
  - Clue states:
    - `UNANSWERED`: Clickable, show dollar value only
    - `ANSWERED`: Show question, show wager input (if Daily Double)
    - `RESOLVED`: Show question and answer, show score delta, disabled
  - Score: Display current score from `game.score`
- **FINAL_PENDING state**:
  - Show: Final Jeopardy category, wager input form
  - Hide: Game board
  - Wager input: Min $0, Max `game.score` (backend validates)
- **FINAL_ACTIVE state**:
  - Show: Final Jeopardy question, answer adjudication buttons (Yes/No)
  - Hide: Wager input
  - Display: Current wager amount
- **COMPLETED/ELIMINATED states**:
  - Show: Final score, read-only view of all clues
  - Hide: All interactive elements
  - Disable: All buttons and inputs

## API Integration Details

### API Client Structure

**Base URL**: Configured via environment variable `NEXT_PUBLIC_API_URL`

**Authentication**: All requests include JWT token in `Authorization: Bearer <token>` header

**Error Handling**:
- `401 Unauthorized`: Redirect to `/auth/login`
- `403 Forbidden`: Display error, prevent action
- `404 Not Found`: Display "Game not found" error
- `400 Bad Request`: Display validation error message from response
- `500 Internal Server Error`: Display generic error message

**Request/Response Types**: Match backend DTOs exactly (see Phase 6 plan)

## Authentication Handling

### Supabase Auth Integration

**Configuration**:
- Supabase client initialized in `lib/auth/supabase.ts`
- Uses environment variables: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`

**Token Management**:
- Supabase SDK handles token storage (localStorage/sessionStorage)
- JWT token extracted from Supabase session for API requests
- Token automatically refreshed by Supabase SDK

**Auth State Hooks**:
- `useAuth()` - Returns current user and session
- `useRequireAuth()` - Redirects to login if not authenticated

**Protected Routes**:
- Middleware or route guards check authentication
- Redirect to `/auth/login` if not authenticated
- Extract JWT from Supabase session for API calls

**Auth Flow**:
1. User visits protected route
2. Check Supabase session
3. If no session → redirect to `/auth/login`
4. If session exists → extract JWT token
5. Include JWT in API request headers
6. If API returns 401 → clear session, redirect to login

## UI Responsibilities vs Backend Responsibilities

### Frontend UI Responsibilities

1. **Rendering**:
   - Display game state (score, game status, clues)
   - Render game board layout
   - Show/hide UI elements based on backend state
   - Format data for display (dates, currency, etc.)

2. **User Interactions**:
   - Capture user input (wager amounts, Yes/No answers)
   - Send user actions to backend via API
   - Display loading states during API calls
   - Display success/error messages from API responses

3. **Navigation**:
   - Route between pages
   - Handle browser back/forward
   - Redirect based on authentication state

4. **State Display**:
   - Show which clues are answered/unanswered/resolved (from backend `state` field)
   - Show current score (from backend `score` field)
   - Show game status (from backend `state` field)
   - Enable/disable buttons based on backend state

5. **Data Fetching**:
   - Fetch game data from API
   - Refresh data after user actions
   - Handle pagination for game lists

### Backend Responsibilities (Authoritative)

1. **Business Rules**:
   - Enforce game state transitions
   - Validate wager amounts (min/max bounds)
   - Prevent duplicate submissions
   - Calculate score changes
   - Determine game completion

2. **State Management**:
   - Maintain authoritative game state
   - Track clue states (UNANSWERED, ANSWERED, RESOLVED)
   - Persist all state changes
   - Return current state in API responses

3. **Validation**:
   - Validate all inputs
   - Reject invalid actions (wrong state, unauthorized, etc.)
   - Return descriptive error messages

4. **Authorization**:
   - Verify user owns game
   - Enforce access control

### What Frontend MUST NOT Do

1. **NO Business Logic**:
   - ❌ Calculate score changes locally
   - ❌ Determine if wager is valid (backend validates)
   - ❌ Enforce game state transitions
   - ❌ Determine if clue can be answered
   - ❌ Calculate max wager (backend provides in response)

2. **NO State Derivation**:
   - ❌ Derive game state from local calculations
   - ❌ Infer clue states from local data
   - ❌ Calculate score from local actions
   - ❌ Determine game completion locally

3. **NO Rule Enforcement**:
   - ❌ Prevent actions client-side (backend rejects invalid actions)
   - ❌ Validate wager bounds locally (backend validates)
   - ❌ Enforce "one active game" rule (backend enforces)

4. **NO Optimistic Updates**:
   - ❌ Update UI before API response
   - ❌ Assume action succeeded
   - ❌ Cache state locally (always fetch from backend)

5. **NO Data Transformation**:
   - ❌ Transform backend data for business logic
   - ❌ Filter/aggregate data for rules
   - ❌ Modify backend responses

### Frontend Pattern: "Render What Backend Says"

- Frontend displays exactly what backend returns
- If backend says clue is `RESOLVED`, show as resolved
- If backend says score is `$500`, display `$500`
- If backend says game is `COMPLETED`, show as completed
- If backend rejects action, display error and don't update UI
- Always refresh from backend after actions

## Data Flow Examples

### Example 1: Starting a Game

1. **User Action**: User clicks "Start Game" button on PENDING game
2. **Frontend**: 
   - Disable button, show loading
   - Call `POST /games/:id/start`
   - Include JWT in Authorization header
3. **Backend**:
   - Verify authentication
   - Verify game state is PENDING
   - Create Jeopardy and Double Jeopardy boards
   - Transition game to ACTIVE
   - Return updated game state
4. **Frontend**:
   - Receive response with `state: 'ACTIVE'`
   - Refresh game data (`GET /games/:id`)
   - Fetch board data (`GET /games/:id/board`)
   - Render game board
   - Hide "Start Game" button
   - Show game board

### Example 2: Answering a Clue

1. **User Action**: User clicks on UNANSWERED clue
2. **Frontend**:
   - Display clue question (from board data)
   - Show "I got it right" and "I got it wrong" buttons
3. **User Action**: User clicks "I got it right"
4. **Frontend**:
   - Call `POST /games/:id/clues/:clueId/answer` with `{ correct: true }`
   - Include JWT in Authorization header
   - Show loading state
5. **Backend**:
   - Verify authentication and authorization
   - Verify game state is ACTIVE
   - Verify clue state is UNANSWERED or ANSWERED
   - Calculate score change
   - Update clue state to RESOLVED
   - Update game score
   - Check if all clues resolved → transition to FINAL_PENDING if so
   - Return updated clue and new score
6. **Frontend**:
   - Receive response with `state: 'RESOLVED'`, `scoreDelta`, `newScore`
   - Refresh game data (`GET /games/:id`)
   - Refresh board data (`GET /games/:id/board`)
   - Update UI to show clue as resolved
   - Display correct answer
   - Update score display
   - If game state changed to FINAL_PENDING, show Final Jeopardy view

### Example 3: Submitting Daily Double Wager

1. **User Action**: User clicks on Daily Double clue (UNANSWERED)
2. **Frontend**:
   - Display clue question
   - Show wager input form
   - Fetch current game state to get score
3. **User Action**: User enters wager amount and submits
4. **Frontend**:
   - Call `POST /games/:id/clues/:clueId/wager` with `{ wager: 500 }`
   - Include JWT in Authorization header
   - Show loading state
5. **Backend**:
   - Verify authentication and authorization
   - Verify game state is ACTIVE
   - Verify clue is Daily Double
   - Verify clue state is UNANSWERED
   - Validate wager (min $5, max based on score and round)
   - Update clue with wager
   - Transition clue state to ANSWERED
   - Return updated clue
6. **Frontend**:
   - Receive response
   - Refresh board data
   - Show answer adjudication buttons (clue now in ANSWERED state)
   - Display error if backend rejected (e.g., wager too high)

## Error Handling Strategy

### API Error Handling

1. **401 Unauthorized**:
   - Clear Supabase session
   - Redirect to `/auth/login`
   - Display message: "Please log in to continue"

2. **403 Forbidden**:
   - Display error: "You don't have access to this resource"
   - Prevent action
   - Optionally redirect to `/games`

3. **404 Not Found**:
   - Display error: "Game not found" or "Resource not found"
   - Optionally redirect to `/games`

4. **400 Bad Request**:
   - Display error message from API response
   - Keep user on current page
   - Allow user to correct input

5. **500 Internal Server Error**:
   - Display generic error: "Something went wrong. Please try again."
   - Log error for debugging
   - Allow user to retry

### Network Error Handling

- Display "Network error. Please check your connection."
- Allow user to retry
- No automatic retries (keep simple)

## Constraints

1. **Backend Authority**:
   - Backend API contracts are locked and authoritative
   - Frontend must not modify or extend API contracts
   - All validation comes from backend responses

2. **No Business Logic**:
   - Frontend only displays and captures user input
   - All calculations, validations, and state transitions happen on backend

3. **State Reflection**:
   - Frontend reflects backend state exactly
   - No derived state or client-side calculations
   - Always fetch fresh data from backend after actions

4. **Simplicity**:
   - Keep UI simple and functional
   - No advanced features or optimizations
   - Focus on correctness over polish

5. **Type Safety**:
   - Use TypeScript throughout
   - Types must match backend DTOs exactly
   - No `any` types (except for error handling)
