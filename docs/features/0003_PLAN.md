# Final Jeopardy Clues Database Ingestion Plan

## Description

Implement a database ingestion service to persist parsed Final Jeopardy clues into the database. The service must be idempotent, handle duplicates gracefully, validate all required fields, and provide comprehensive logging. This supports Phase 4 of the implementation roadmap.

## Files to Create

- `backend/src/data/ingestion/final-jeopardy-ingestion.service.ts` - Main ingestion service
- `backend/src/data/ingestion/final-jeopardy-ingestion.service.spec.ts` - Unit tests

## Data Structure

### Input
- **File**: `backend/data/jeopardy_clue_dataset/parsed/final-jeopardy-clues.json`
- **Structure**:
  ```typescript
  {
    metadata: {
      totalClues: number,
      totalFilesProcessed: number,
      // ... other metadata
    },
    clues: ParsedFinalJeopardyClue[]
  }
  ```
- **ParsedFinalJeopardyClue** (from `backend/src/data/parsing/types.ts`):
  - `seasonNumber: number` (33-41)
  - `category: string` (non-empty)
  - `answer: string` (non-empty)
  - `question: string` (non-empty)
  - `airDate?: string` (optional)
  - `sourceFile: string` (for traceability)

### Database Schema (Clue Model)
- `id: String` (auto-generated cuid)
- `category: String` (required)
- `round: Round` (must be `FINAL`)
- `value: Int` (must be `0` for Final Jeopardy)
- `question: String` (required)
- `answer: String` (required)
- `dailyDouble: Boolean` (must be `false` for Final Jeopardy)
- `createdAt: DateTime` (auto-generated)

**Note**: The Prisma schema does not currently include `seasonNumber`, `airDate`, or `sourceFile` fields. These are metadata from the parsed file but are not required for game functionality. They can be logged for traceability but do not need to be stored in the database unless schema changes are made.

## Algorithm

### Step 1: Read and Parse Input File
1. Resolve path to `backend/data/jeopardy_clue_dataset/parsed/final-jeopardy-clues.json`
2. Read file content using `fs/promises`
3. Parse JSON content
4. Extract `clues` array from parsed data
5. Validate file structure (must have `clues` array)

### Step 2: Validate Clues
For each clue in the array:
1. Validate required fields:
   - `category`: must be non-empty string (after trimming)
   - `answer`: must be non-empty string (after trimming)
   - `question`: must be non-empty string (after trimming)
2. Skip invalid clues and log validation errors
3. Track count of invalid clues

### Step 3: Check for Existing Clues (Deduplication)
For each valid clue:
1. Create deduplication key: `category|question|answer` (same as parser service)
2. Query database for existing clue with:
   - `round = FINAL`
   - `category = clue.category` (exact match, case-sensitive)
   - `question = clue.question` (exact match)
   - `answer = clue.answer` (exact match)
3. If clue exists:
   - Skip insertion
   - Increment `duplicatesSkipped` counter
   - Log as duplicate (debug level)
4. If clue does not exist:
   - Add to insertion batch

**Optimization**: Consider batch querying existing clues to reduce database round trips. Query all potential duplicates in one or a few queries, then check in-memory.

### Step 4: Insert Clues
For each unique clue:
1. Create Clue record with:
   - `category`: from parsed clue (trimmed)
   - `round`: `Round.FINAL` (enum value)
   - `value`: `0` (Final Jeopardy has no dollar value)
   - `question`: from parsed clue (trimmed)
   - `answer`: from parsed clue (trimmed)
   - `dailyDouble`: `false` (Final Jeopardy is never a Daily Double)
2. Use Prisma `create` operation via `PrismaService.client.clue.create()`
3. Track successful insertions
4. Handle database errors (constraint violations, connection issues)

**Batch Insertion**: Consider using Prisma's `createMany` for better performance, but note that `createMany` doesn't return created records and has limitations. Alternatively, use transactions to batch multiple `create` operations.

### Step 5: Logging and Results
1. Log summary statistics:
   - Total clues processed
   - Valid clues
   - Invalid clues (with reasons)
   - Clues inserted
   - Duplicates skipped
   - Errors encountered
2. Return ingestion result object with all counts

## Deduplication Strategy

### In-Memory Deduplication (Within Ingestion Run)
- Track seen clues in current batch using Set of deduplication keys
- Skip duplicates within the same ingestion run before database queries

### Database-Level Deduplication
- Query existing clues matching the deduplication criteria
- Use Prisma query:
  ```typescript
  await prisma.clue.findFirst({
    where: {
      round: Round.FINAL,
      category: clue.category,
      question: clue.question,
      answer: clue.answer,
    },
  });
  ```

### Idempotency
- Running the ingestion multiple times should produce the same result
- Existing clues are skipped, only new clues are inserted
- No updates to existing clues (per schema immutability rule)

## Error Handling

### File Read Errors
- File not found: Log error, exit with error code
- Invalid JSON: Log parsing error, exit with error code
- Missing `clues` array: Log error, exit with error code

### Validation Errors
- Invalid clue fields: Log warning, skip clue, continue processing
- Track invalid clues separately from database errors

### Database Errors
- Connection errors: Log error, exit with error code
- Constraint violations: Log error for specific clue, continue with others
- Transaction failures: Rollback, log error, exit with error code

### Partial Failures
- If some clues fail to insert but others succeed, log all failures
- Return result with counts of successful and failed insertions
- Allow caller to decide if partial success is acceptable

## Performance Considerations

1. **Batch Processing**: Process clues in batches (e.g., 100-500 at a time) to avoid memory issues
2. **Database Queries**: Consider batch querying existing clues to reduce round trips
3. **Transactions**: Use transactions for batch inserts to ensure atomicity
4. **Logging**: Use appropriate log levels (debug for duplicates, info for summary, error for failures)

## Validation Rules

### Required Field Validation
- `category`: Non-empty string after trimming
- `answer`: Non-empty string after trimming
- `question`: Non-empty string after trimming

### Database Constraints
- `round` must be `Round.FINAL`
- `value` must be `0`
- `dailyDouble` must be `false`
- All string fields must be non-empty (enforced by validation before insertion)

### Business Rules
- Clues are immutable after creation (per schema comment)
- No updates to existing clues
- Duplicates are identified by exact match of category, question, and answer

## Exit Conditions

The ingestion is complete when:
- All valid clues from the parsed file have been processed
- All unique clues have been inserted into the database
- All duplicates have been identified and skipped
- Comprehensive logging has been generated
- Result object has been returned with accurate counts

The database is ready for game creation endpoints when:
- Final Jeopardy clues exist in the database with `round = FINAL`
- Sufficient clues are available for game creation (validation can check count)
- All clues have valid required fields
