# Feature 0016: Comprehensive Testing & Validation

## Description

Implement a robust testing suite to validate backend business logic, API endpoints, and critical frontend interactions. Ensure deterministic, repeatable behavior and enforce domain rules, state transitions, authentication, and user stats updates.

## Scope

- Backend unit tests for services and domain logic
- Backend integration tests for API endpoints with authentication
- Edge case and negative tests
- Frontend component rendering and interaction tests (React Testing Library)
- Mocking external dependencies (e.g., Cluebase API)
- Test database setup with predictable seed data and transactional isolation (optional; integration tests use mocked Prisma by default)

## Files and Directories

### Created

- **`backend/tests/unit/`** — Unit tests for services (e.g. `game.service.unit.spec.ts` for `GameService.answerClue()`, `startGame()`).
- **`backend/tests/integration/`** — Integration tests for API (e.g. `games.api.integration-spec.ts`). Uses `AppModule` with Prisma overridden by a seeded mock.
- **`backend/tests/integration/jest-integration.json`** — Jest config for integration tests.
- **`backend/jest.config.js`** — Jest config for unit tests (roots: `src`, `tests/unit`).
- **`backend/tests/README.md`** — Describes test structure, commands, and mocking.
- **`frontend/src/__tests__/`** — Critical flow tests (e.g. `critical-flows.test.tsx` for board state, ScoreDisplay, dashboard summary, ClueCard states).

### Modified

- **`backend/package.json`** — `test` / `test:watch` / `test:cov` use `jest.config.js`; added `test:integration` script.
- **`backend/src/game/game.service.spec.ts`** — Added UserService mock and Prisma `user` mock; fixed `selectFinalJeopardyClue` expectation (no `take: 1`).
- **`backend/src/user/user.service.spec.ts`** — Fixed expectations for `updateUserStatsOnClueResolved` and `updateUserStatsOnGameComplete` to use explicit numeric updates (not Prisma `increment`).

## Implementation Phases

### Phase 1: Backend Unit Tests

- Unit tests for **GameService**: `answerClue()` (score calculation, already resolved, wrong game, Daily Double wager, user stats), `startGame()` (game not found, not PENDING, wrong user). Implemented in `tests/unit/game.service.unit.spec.ts` with mocked Prisma and UserService.
- **UserService**: `updateUserStatsOnClueResolved()` and related stats logic already covered in `src/user/user.service.spec.ts`; expectations aligned with actual implementation (explicit numbers, not `increment`).
- **CluebaseService**: Not present in codebase; clues are loaded from DB (ingestion from files). No Cluebase API to mock.

### Phase 2: Backend Integration Tests

- **Test DB**: Integration tests use a **mocked** Prisma with seeded data so they run without a real database and remain deterministic.
- **API tests**: `tests/integration/games.api.integration-spec.ts` — Auth (401 without/invalid token, 200 with valid JWT), game creation (POST /games 201, validation), game retrieval (GET /games/:id 401/200).
- **Authentication**: Valid JWT from `generateTestToken` (test secret); missing/invalid token returns 401.

### Phase 3: Frontend Component Tests

- **`frontend/src/__tests__/critical-flows.test.tsx`**: Renders board from API state; clicking clue invokes callback; answered clue disabled; ScoreDisplay positive/negative/zero; SummarySection stats and N/A; ClueCard UNANSWERED vs ANSWERED.
- Existing component tests remain in `components/game/__tests__/`, `app/games/[id]/__tests__/`, `store/__tests__/`, `hooks/__tests__/`.

### Phase 4: Mock External Dependencies

- Backend: Prisma is mocked in unit and integration tests; no network or DB required.
- Frontend: API calls are mocked in page/hook tests (e.g. `jest.mock('@/lib/api/games')`). Critical-flows tests use components with props only (no API calls).

## Exit Conditions

- All unit tests pass deterministically (`npm run test`).
- All integration tests pass with mocked Prisma and JWT (`npm run test:integration`).
- Frontend critical-flows and existing component tests pass (`npm run test` in frontend).
- Edge cases and negative scenarios covered (e.g. 401, invalid state, already resolved clue).
- Test layout documented in `backend/tests/README.md`.
