# Create Game (Final Jeopardy only) Plan

## Description

Implement a service to create a new game and associate exactly one Final Jeopardy clue. The game is initialized with a PENDING state, and a Final Jeopardy clue is selected deterministically from available clues in the database. Clue selection is internal to the service, and no clue mutation occurs. This supports Phase 5 of the implementation roadmap.

## Data Structure

### Input
- **userId**: `string` (required) - The authenticated user creating the game
- No other input parameters required

### Database Operations

#### Game Creation
- Create `Game` record with:
  - `userId`: from input
  - `state`: `GameState.PENDING` (default)
  - `score`: `0` (default)
  - `createdAt`: auto-generated
  - `updatedAt`: auto-generated

#### Final Jeopardy Clue Selection
- Query `Clue` table for:
  - `round = Round.FINAL`
  - At least one clue must exist (validation)
- Selection algorithm: Deterministic selection using a simple approach

#### FinalJeopardy Association
- Create `FinalJeopardy` record with:
  - `gameId`: from created game
  - `clueId`: from selected clue
  - `wager`: `0` (initial value, updated when player submits wager)
  - `correct`: `null` (not yet answered)
  - `scoreDelta`: `null` (not yet calculated)
  - `answeredAt`: `null` (not yet answered)

### Output
- Return created game with:
  - Game record (id, userId, state, score, timestamps)
  - Associated FinalJeopardy record with clue details
  - Selected clue information (category, question, answer)

## Algorithm

### Step 1: Validate User
1. Verify `userId` is provided and non-empty
2. (Optional) Verify user exists in database (if user validation is required)

### Step 2: Select Final Jeopardy Clue
1. Query database for all clues where `round = Round.FINAL`
2. Validate at least one clue exists
3. If no clues exist, throw error: "No Final Jeopardy clues available"
4. Apply deterministic selection algorithm:
   - **Algorithm**: Select a random clue using a seeded random number generator
   - **Seed**: Use current timestamp (milliseconds since epoch) as seed
   - **Implementation**: 
     - Get count of available clues
     - Generate random index: `Math.floor(Math.random() * clueCount)`
     - Select clue at that index
   - **Alternative (simpler)**: Select first available clue (deterministic but predictable)
   - **Note**: The selection algorithm must be explicitly defined and documented in code comments

### Step 3: Create Game Record
1. Create `Game` record using Prisma:
   ```typescript
   await prisma.game.create({
     data: {
       userId,
       state: GameState.PENDING,
       score: 0,
     },
   });
   ```

### Step 4: Create FinalJeopardy Association
1. Create `FinalJeopardy` record linking game to selected clue:
   ```typescript
   await prisma.finalJeopardy.create({
     data: {
       gameId: game.id,
       clueId: selectedClue.id,
       wager: 0, // Initial value, updated when player submits wager
     },
   });
   ```

### Step 5: Return Game State
1. Fetch complete game with relations:
   - Include `finalJeopardy` relation
   - Include `finalJeopardy.clue` relation
2. Return game object with all associated data

## Error Handling

### Validation Errors
- Missing or empty `userId`: Throw error with message "User ID is required"
- User does not exist: Throw error with message "User not found" (if user validation is implemented)

### Business Logic Errors
- No Final Jeopardy clues available: Throw error with message "No Final Jeopardy clues available in database"

## Clue Selection Determinism

The clue selection algorithm must be deterministic and explicitly defined:

### Option 1: Random Selection (Seeded)
- Use current timestamp as seed for random number generation
- Select clue at random index from available clues
- **Pros**: Provides variety in clue selection
- **Cons**: Not truly deterministic (depends on timing)

### Option 2: Round-Robin Selection
- Track last selected clue index (stored in memory or database)
- Select next clue in sequence
- **Pros**: Truly deterministic, ensures all clues are used
- **Cons**: Requires state tracking

### Option 3: First Available (Simplest)
- Always select first clue from query results
- **Pros**: Simple, deterministic, no state required
- **Cons**: Always same clue (unless clues are added/removed)

### Recommendation
Use **Option 3 (First Available)** for initial implementation:
- Simplest to implement and test
- Deterministic behavior
- No state management required
- Can be enhanced later if variety is needed

## Transaction Handling

All database operations (game creation + FinalJeopardy association) should be wrapped in a transaction to ensure atomicity:
- If game creation succeeds but FinalJeopardy creation fails, rollback game creation
- If clue selection fails, no database changes occur

## Constraints

- **Clue selection is internal**: No external input for clue selection
- **No clue mutation**: Clue records are never modified, only read
- **Deterministic behavior**: Selection algorithm must be explicitly defined and consistent
- **Single Final Jeopardy clue**: Exactly one clue is associated per game
- **Initial wager**: Set to 0, updated later when player submits wager

## Testing Strategy

### Unit Tests
1. **Game Creation**
   - Test successful game creation with valid userId
   - Test game state is PENDING
   - Test score is 0

2. **Clue Selection**
   - Test selection when clues exist
   - Test error when no clues exist
   - Test deterministic selection (same input = same output)

3. **FinalJeopardy Association**
   - Test FinalJeopardy record is created
   - Test correct gameId and clueId are set
   - Test initial wager is 0

4. **Error Handling**
   - Test validation errors (missing userId)
   - Test business logic errors (no clues available)
   - Test database errors (connection failures)

5. **Transaction Handling**
   - Test rollback on FinalJeopardy creation failure
   - Test atomicity of operations

### Integration Tests
1. **End-to-End Game Creation**
   - Create game with real database
   - Verify all records are created correctly
   - Verify game state is correct

2. **Multiple Game Creations**
   - Create multiple games
   - Verify each gets a clue (may be same or different based on algorithm)
   - Verify no conflicts or duplicates

## Performance Considerations

1. **Clue Query**: Query should be efficient with existing index on `(round, category, question, answer)`
2. **Transaction Size**: Minimal operations in transaction (game + FinalJeopardy creation)
3. **Query Optimization**: Use `findFirst` or `findMany` with limit 1 for clue selection

## Exit Conditions

The game creation is complete when:
- Game record is created with PENDING state
- Final Jeopardy clue is selected deterministically
- FinalJeopardy association record is created
- Complete game state is returned with all relations
- All operations are atomic (transaction succeeds or fails as a unit)

The game is ready for:
- Player to view the Final Jeopardy clue
- Player to submit a wager
- Game state progression to FINAL_PENDING or FINAL_ACTIVE
