# Feature 0017: Shadcn UI Integration for Frontend

## Description

Plan the adoption of Shadcn UI as the component library to modernize the frontend. Focus on architecture, theming, SCSS integration, and incremental adoption. No component implementation in this plan — the deliverable is a structured roadmap for integration.

**Goals:** Provide consistent, modern, and accessible UI components; reduce inline CSS and improve maintainability; leverage TypeScript-friendly components; integrate with existing SCSS structure; enable responsive design and consistent layout patterns.

**Reasons to choose Shadcn UI:** Built on Tailwind for rapid styling; fully TypeScript-compatible and React 18–ready; accessible and composable components (modals, buttons, inputs, tables); good documentation and community support; easy to extend and theme.

---

## Directory Structure (Target)

- **`frontend/src/components/ui/`** — Shadcn-wrapped or custom reusable components (current: `Button.tsx`, `ErrorDisplay.tsx`, `LoadingSpinner.tsx`).
- **`frontend/src/styles/components/`** — Component-specific SCSS overrides or extensions for Shadcn (current SCSS files: Button, ClueCard, DashboardSection, GameBoard, GameCard, GameList, etc.).
- **`frontend/src/styles/`** — `_globals.scss`, `_variables.scss`, `_mixins.scss`, `main.scss`.

---

## Relevant Files and Directories

### Configuration and entry

- **`frontend/package.json`** — Add Shadcn CLI and any Shadcn/Radix dependencies introduced by `npx shadcn@latest init` and component adds.
- **`frontend/tailwind.config.js`** — Extend theme with Shadcn tokens (colors, radius, spacing); ensure `content` includes Shadcn component paths (e.g. `./src/components/ui/**/*.tsx`).
- **`frontend/postcss.config.js`** — No change expected unless Shadcn docs require it.
- **`frontend/src/app/globals.css`** — Shadcn injects CSS variables for theming (e.g. `--background`, `--foreground`, `--primary`); these must be defined or overridden here (or in a shared layer) so Tailwind and Shadcn share tokens.
- **`frontend/src/app/layout.tsx`** — Imports `globals.css` and `@/styles/main.scss`; ensure Shadcn theme CSS is loaded (typically via globals.css) and load order does not break existing SCSS (globals, app-root).
- **`frontend/src/styles/main.scss`** — Entry that imports `_variables`, `_mixins`, `_globals`. Must remain the single place for global SCSS; do not duplicate Shadcn theme variables here unless intentionally syncing SCSS variables to Tailwind/Shadcn tokens.

### Theming and tokens

- **`frontend/src/styles/_variables.scss`** — Current tokens: `$color-primary`, `$color-primary-dark`, `$color-border`, `$color-clue-value`, `$color-cyan`, `$color-negative`, spacing, font-family, breakpoints. Plan: map these to Tailwind/Shadcn theme so one source of truth drives both Tailwind utility classes and Shadcn components (e.g. define CSS custom properties in globals.css from these values, or define Tailwind `theme.extend.colors` from the same palette and keep SCSS variables in sync via documentation or a small build step).
- **`frontend/src/styles/_globals.scss`** — Body and `.app-root` (gradient, flex). Must remain compatible with Shadcn base styles; avoid overriding Shadcn CSS variables unless intentional.

### Components to map and migrate (incremental)

- **`frontend/src/components/ui/Button.tsx`** — Uses `btn btn--primary|secondary|danger` and `Button.scss`. Replace or wrap with Shadcn Button; keep or move variant semantics into Shadcn variants; SCSS in `styles/components/Button.scss` becomes overrides only if needed.
- **`frontend/src/components/ui/ErrorDisplay.tsx`** — Candidate for Shadcn Alert or custom composition.
- **`frontend/src/components/ui/LoadingSpinner.tsx`** — Candidate for Shadcn loading pattern or keep as custom with Shadcn-compatible classes.
- **Form inputs:** **`frontend/src/components/game/WagerInput.tsx`** uses a raw `<input>` with Tailwind/SCSS classes; **`frontend/src/app/auth/login/page.tsx`** uses inputs for login. Map to Shadcn Input (and Label if used); style via Tailwind theme + optional SCSS in `styles/components/WagerInput.scss`, `LoginPage.scss`.
- **Cards / surfaces:** **`frontend/src/components/game/GameCard.tsx`**, **`frontend/src/components/dashboard/*`** (SummarySection, AccuracySection, StreaksSection, WagersSection) use section/card-like layout with `dashboard-section` and SCSS. Plan Shadcn Card for shared card surface; keep or refactor dashboard SCSS to overrides.
- **Modals / overlays:** **`frontend/src/app/games/[id]/page.tsx`** uses a modal-like overlay for selected clue (clue question/answer). Map to Shadcn Dialog or Sheet for accessibility and consistency.
- **Game board:** **`frontend/src/components/game/GameBoard.tsx`**, **ClueCard.tsx** — More complex; migrate after buttons, inputs, cards, and dialogs. Use Shadcn for any shared primitives (e.g. Button for clue cells if applicable); keep game-specific layout in SCSS or Tailwind.

### Layout

- **`frontend/src/components/layout/Header.tsx`**, **Footer.tsx** — Use existing SCSS; optionally adopt Shadcn navigation or container patterns in a later phase.

### SCSS component styles (overrides after Shadcn)

- **`frontend/src/styles/components/*.scss`** — Each corresponds to a component (Button, ClueCard, DashboardSection, GameBoard, GameCard, GameList, Header, Footer, LoginPage, WagerInput, ScoreDisplay, AnswerAdjudication, FinalJeopardyView, GameDetailPage). After Shadcn adoption: use only for overrides or extensions that cannot be expressed with Tailwind/Shadcn theme (e.g. game-board gradient, clue value color). Minimize duplication with Shadcn theme.

## Phases

### Phase 1: Shadcn setup and theming

1. Install Shadcn UI and Tailwind dependencies per Shadcn docs (e.g. `npx shadcn@latest init` for Next.js App Router); confirm compatibility with Next 14 and React 18.
2. Configure the Tailwind theme and tokens to match existing SCSS variables: map `_variables.scss` colors (e.g. `$color-primary`, `$color-primary-dark`, `$color-border`, `$color-clue-value`, `$color-cyan`, `$color-negative`) and spacing into `tailwind.config.js` `theme.extend` and/or CSS variables in `globals.css` that Shadcn expects.
3. Ensure global SCSS variables (colors, typography) stay in sync with the Shadcn theme — either by driving Tailwind/Shadcn from the same tokens (e.g. globals.css CSS vars sourced from design tokens) or by documenting and manually keeping `_variables.scss` and Tailwind theme aligned.
4. Validate base layouts, typography, and spacing: run app with existing pages; confirm `_globals.scss` (body, `.app-root`) still applies correctly and no regressions from Shadcn base styles.

**Files touched:** `package.json`, `tailwind.config.js`, `globals.css`, optionally `_variables.scss` or a tokens file; `layout.tsx` only if import order changes.

---

### Phase 2: Component mapping and refactoring plan

1. **Inventory current UI:** Buttons (ui/Button), inputs (WagerInput, login page), modals/overlays (game detail clue modal), dashboard cards (SummarySection, AccuracySection, StreaksSection, WagersSection), game board and clue cards (GameBoard, ClueCard, GameCard), layout (Header, Footer), ErrorDisplay, LoadingSpinner.
2. **Map to Shadcn:** Buttons → Shadcn Button; form fields → Shadcn Input, Label; card surfaces → Shadcn Card; overlay for clue → Shadcn Dialog or Sheet; tables (if any) → Shadcn Table; alerts → Shadcn Alert.
3. **Order of migration (incremental, low-risk first):** (1) Button, (2) Input/Label (WagerInput, login), (3) Card (dashboard sections, GameCard), (4) Dialog/Sheet (clue modal), (5) GameBoard/ClueCard and remaining layout. Document this order in the codebase or this plan so implementation follows it.

**Deliverable:** A short mapping table or list (in this doc or a REFACTOR.md in frontend) listing each current component, its Shadcn counterpart, and whether it will be replaced vs wrapped.

---

### Phase 3: Incremental integration

1. **Per component (e.g. Button first):** Add Shadcn component (e.g. `npx shadcn@latest add button`); wrap or replace existing `components/ui/Button` with Shadcn Button; preserve variant API (primary, secondary, danger) via Shadcn variants or className; adjust SCSS in `styles/components/Button.scss` only for overrides (e.g. brand colors not in theme).
2. **Repeat for Input, Card, Dialog, etc.:** Same pattern — add Shadcn component, swap into consuming components, keep or add SCSS overrides only where needed.
3. **Consuming components:** Update `AnswerAdjudication`, `FinalJeopardyView`, `GameList`, `GameCard`, `WagerInput`, login page, game detail page, dashboard sections to use the new Shadcn-backed primitives; avoid new inline CSS.
4. **Testing:** After each swap, test visual consistency, responsiveness, and accessibility (focus order, contrast, keyboard, and screen reader where applicable).

**Files touched:** All component files under `components/ui/`, `components/game/`, `components/dashboard/`, `components/layout/`, and `app/auth/login/page.tsx`, `app/games/[id]/page.tsx`; and the corresponding `styles/components/*.scss` files.

---

### Phase 4: Validation and exit criteria

1. **Inline CSS:** Minimized or removed; styling lives in Tailwind theme, Shadcn components, or SCSS overrides in `styles/components/`.
2. **Major flows:** All major UI flows (login, game list, game detail, board, clue modal, dashboard) use Shadcn components where mapped.
3. **Consistency:** Layouts and interactions are consistent across pages; Tailwind tokens and SCSS variables remain synchronized (single source of truth or documented sync).
4. **Accessibility:** Basic checks pass — focus visible, contrast sufficient, screen reader usability for buttons, links, form labels, and dialogs.

**No new code in this plan;** validation is done via manual or automated checks during implementation.
