# Phase 9: Frontend Testing & Validation - Implementation Plan

## Description

Add comprehensive automated testing and validation to the frontend application to verify correctness, prevent regressions, and ensure predictable behavior under normal and edge-case conditions. This phase focuses on testing Redux-based state management, polling behavior, state transitions, error handling, and recovery mechanisms. No new product features or UI changes will be introduced.

## Algorithms and Testing Strategies

### 1. Redux Store Testing Strategy

**Problem**: Redux slices contain complex logic with async thunks, state transitions, and side effects that need comprehensive testing.

**Solution**: Test Redux logic in isolation using Redux Toolkit's testing utilities:

**Algorithm**:
```
1. For synchronous reducers:
   a. Create initial state
   b. Dispatch action with payload
   c. Assert state changes match expected values
   d. Test edge cases (null, undefined, empty values)

2. For async thunks:
   a. Mock API functions using jest.mock or MSW
   b. Create mock store with configureStore
   c. Dispatch thunk
   d. Wait for thunk to complete (fulfilled or rejected)
   e. Assert:
      - Correct API calls were made
      - State updated correctly
      - Side effects (dispatch calls) occurred
      - Error handling worked as expected

3. For extraReducers:
   a. Dispatch thunk that triggers extraReducer
   b. Assert state changes in pending, fulfilled, rejected cases
   c. Test state transitions (previousGameState tracking)
   d. Test side effects (selectedClue clearing, polling updates)
```

### 2. Polling Behavior Testing Strategy

**Problem**: Polling involves timers, intervals, and cleanup that are difficult to test deterministically.

**Solution**: Use Jest fake timers and mock setInterval/clearInterval:

**Algorithm**:
```
1. Enable Jest fake timers before tests
2. Mock setInterval and clearInterval to track calls
3. Test startPolling:
   a. Dispatch startPolling with gameId
   b. Assert interval was created
   c. Fast-forward timer to trigger interval callback
   d. Assert fetchGameData was dispatched
   e. Test that actionLoading prevents polling
   f. Test that state change stops polling
4. Test stopPolling:
   a. Start polling first
   b. Dispatch stopPolling
   c. Assert clearInterval was called with correct ID
   d. Assert isPolling is false
5. Test cleanup:
   a. Start polling
   b. Dispatch resetGameState
   c. Assert interval was cleared
6. Test race conditions:
   a. Start polling, get interval ID
   b. Stop polling (clears interval)
   c. Fast-forward timer
   d. Assert fetchGameData was NOT dispatched (interval ID mismatch check worked)
```

### 3. State Transition Testing Strategy

**Problem**: Game state transitions involve multiple reducers and side effects that must be tested together.

**Solution**: Test state transitions end-to-end through thunk dispatch:

**Algorithm**:
```
1. Set up initial state (e.g., PENDING game)
2. Dispatch action that triggers transition (e.g., startGame)
3. Wait for thunk to complete
4. Assert:
   a. Game state changed correctly
   b. previousGameState was updated
   c. Side effects occurred (selectedClue cleared if needed)
   d. Polling started/stopped as appropriate
5. Test each transition:
   - PENDING → ACTIVE
   - ACTIVE → FINAL_PENDING (via fetchGameData detecting change)
   - FINAL_PENDING → FINAL_ACTIVE
   - Any → COMPLETED/ELIMINATED
6. Test selectedClue lifecycle:
   - Set via selectClue
   - Cleared on major state changes
   - Cleared when clue becomes RESOLVED
   - Updated with maxWager after wager submission
```

### 4. Error Handling Testing Strategy

**Problem**: Error handling involves multiple code paths (API errors, network errors, validation errors) that must all be tested.

**Solution**: Mock API responses to simulate different error scenarios:

**Algorithm**:
```
1. For each thunk that can fail:
   a. Mock API to return error response:
      - 400 (validation) - test error message stored
      - 401 (unauthorized) - test error stored, component handles redirect
      - 403 (forbidden) - test error stored, component handles redirect
      - 404 (not found) - test error message stored
      - 500 (server error) - test error message stored
      - Network error (fetch throws) - test error message stored
   b. Dispatch thunk
   c. Wait for rejection
   d. Assert:
      - Error state updated correctly
      - actionLoading cleared
      - Error message is user-friendly
2. Test error recovery:
   a. Set error state
   b. Dispatch successful action
   c. Assert error cleared
3. Test error clearing on retry:
   a. Set error state
   b. Dispatch same action again (pending)
   c. Assert error cleared (pending case clears error)
   d. Complete action successfully
   e. Assert error remains cleared
```

### 5. Mocking Strategy

**Problem**: Tests need to mock API calls, timers, and Redux store without coupling to implementation details.

**Solution**: Use MSW for API mocking and Jest utilities for timers:

**Algorithm**:
```
1. API Mocking (choose one approach):
   Option A: MSW (Mock Service Worker)
   a. Set up MSW handlers in setupTests.ts
   b. Create handlers for each API endpoint
   c. Use server.use() in tests to override handlers
   d. Benefits: Works with fetch, realistic, can test network errors
   
   Option B: jest.mock for API module
   a. Mock @/lib/api/games module
   b. Create mock implementations for each function
   c. Use mockResolvedValue/mockRejectedValue in tests
   d. Benefits: Simple, fast, good for unit tests

2. Timer Mocking:
   a. Use jest.useFakeTimers() in test setup
   b. Use jest.advanceTimersByTime() to trigger intervals
   c. Use jest.runOnlyPendingTimers() to run pending timers
   d. Restore real timers in cleanup

3. Redux Store Mocking:
   a. Use configureStore from @reduxjs/toolkit
   b. Pass preloadedState for initial state
   c. Use createMockStore helper for common scenarios
   d. Test with real reducers (not mocked) for integration tests
```

## Test Categories and Scope

### High Priority Tests (Critical Path)

1. **Redux Thunk Success Paths** - All thunks complete successfully
   - fetchGameData, startGame, selectClue, answerClue, submitClueWager, submitFinalJeopardyWager, answerFinalJeopardy
   - Verify state updates correctly
   - Verify side effects occur

2. **Polling Lifecycle** - Polling starts, runs, and stops correctly
   - Start polling for ACTIVE games
   - Polling pauses during actionLoading
   - Polling stops on terminal states
   - Cleanup on unmount

3. **State Transitions** - Game flows through all states correctly
   - Round transitions (Jeopardy → Double Jeopardy → Final Jeopardy)
   - Terminal states (COMPLETED, ELIMINATED)
   - selectedClue lifecycle

4. **Error Handling** - Errors are caught and handled gracefully
   - API errors (400, 401, 403, 404, 500)
   - Network errors
   - Error state clearing on recovery

### Medium Priority Tests (Edge Cases)

1. **Concurrent Actions** - Multiple actions don't interfere
   - Polling during actionLoading
   - Rapid state changes
   - Race conditions in polling

2. **Edge Cases** - Unusual but valid scenarios
   - Empty board data
   - Missing game data
   - Invalid clue selections
   - Wager validation edge cases

3. **Component Integration** - Components work with Redux
   - Game page initializes correctly
   - Components reflect Redux state
   - User interactions dispatch correct thunks

### Lower Priority Tests (Nice to Have)

1. **Performance** - No performance regressions
   - Polling doesn't cause excessive re-renders
   - State updates are efficient

2. **Accessibility** - Basic a11y checks
   - Error messages are accessible
   - Loading states are announced

## Testing Best Practices

1. **Isolation**: Each test should be independent and not rely on other tests
2. **Determinism**: Use fake timers and mocked APIs for predictable tests
3. **Coverage**: Aim for high coverage on critical paths (thunks, reducers, state transitions)
4. **Readability**: Test names should clearly describe what is being tested
5. **Maintainability**: Use helper functions and mock builders to reduce duplication
6. **Speed**: Keep tests fast by mocking external dependencies
7. **Realism**: Use realistic mock data that matches actual API responses

## High-Risk Areas to Prioritize

1. **Polling Logic** - Complex timer management, race conditions, cleanup
2. **State Transitions** - Multiple reducers involved, side effects
3. **Error Recovery** - Error state must clear correctly, UI must not get stuck
4. **Concurrent Actions** - Polling + user actions must not interfere
5. **selectedClue Lifecycle** - Must be set, updated, and cleared at correct times
6. **API Error Handling** - All error types must be handled gracefully

## Constraints

- No new UI features or visual changes
- No backend changes
- Focus on correctness, resilience, and maintainability
- Tests should reflect actual application behavior and Redux flow
- Prefer deterministic, isolated tests over brittle integration tests
- Tests should run in CI/CD pipeline (must be fast and reliable)
