# Feature 0020: Minimum Deploy Readiness Evaluation

## Purpose

Evaluate whether the project satisfies a **Minimum Deploy Checklist** and determine what work (if any) is required before a first real deployment. This is a planning and evaluation task only — no code, refactors, tests, or configuration changes. Output: readiness summary, structured checklist, and prioritized action plan.

---

## 1. Definition of “Minimum Deployable”

For this project, **minimum deployable** means:

- **Human-usable playable loop:** An authenticated user can sign up/sign in, create a game, start the game, select clues in any order, answer or pass (where allowed), submit Daily Double and Final Jeopardy wagers, receive score updates, and complete or be eliminated from a game. No placeholder or mocked game flow; real backend and persisted state.
- **Backend authority:** All scoring, state transitions, and validation are enforced server-side; frontend only sends intent and reflects server state.
- **Data integrity:** Game and clue state are persisted correctly; no duplicate submissions accepted; ownership enforced so users cannot access or modify other users’ games.
- **Auth in place:** All game-related API calls require a valid Supabase JWT; ownership checks prevent cross-user access.
- **Operational clarity:** Required environment variables are documented; a deployer can configure backend and frontend for a target environment (e.g. hosted backend + frontend) and know what to set. Migrations and data prerequisites (e.g. clue ingestion) are documented so a fresh deploy can be brought up.
- **Baseline stability:** Critical paths do not crash the app; API and auth errors are surfaced to the user (e.g. via ErrorDisplay); no silent failures on core actions.
- **Test confidence:** Core backend domain (game rules, state transitions, auth guard) and critical frontend flows have automated coverage so regressions are detectable; known gaps are documented. Some test failures or env-dependent tests are acceptable if documented and non-blocking.

## 4. Structured Deploy-Readiness Checklist

Use this checklist to decide “ready for first deploy” and to close gaps.

### 4.1 Must have (blocking for first deploy)

- [ ] **Migrations applied:** Document or automate that `prisma migrate deploy` (or equivalent) is run against the deploy database before or at deploy. No schema drift.
- [ ] **Clue data available:** Document that clue ingestion (`ingest:jeopardy`, `ingest:final-jeopardy`) must be run at least once for the deploy DB, or provide a minimal seed/script so a new environment can serve at least one full game.
- [ ] **Deploy env set:** Backend: DATABASE_URL, SUPABASE_*, PORT, FRONTEND_URL (production frontend origin for CORS). Frontend: NEXT_PUBLIC_API_URL (production backend URL), NEXT_PUBLIC_SUPABASE_*. Document in a single “Production / deploy env” section or runbook.
- [ ] **CORS and URL consistency:** FRONTEND_URL and NEXT_PUBLIC_API_URL match the actual production origins; no mixed localhost in production.

### 4.2 Should have (non-blocking but recommended before first deploy)

- [ ] **Deploy runbook:** One concise doc (e.g. `docs/deploy.md` or section in README): order of steps (migrate → ingest if needed → configure env → start backend → build/deploy frontend), and how to verify (e.g. create game, play one clue).
- [ ] **Test expectations:** Document which test suites are required to pass for deploy (e.g. backend unit + game.service only) and which are allowed to fail or are skipped in CI (e.g. integration without DB, or specific frontend tests). Reduces ambiguity and avoids “all green or no deploy” without a path.

### 4.3 Nice to have (deferrable)

- [ ] Centralized error reporting (e.g. Sentry).
- [ ] React error boundary for uncaught frontend errors.
- [ ] Automated “smoke” or E2E test that creates a game and completes one clue after deploy.
- [ ] Production-specific logging (e.g. log level, no PII).

## 5. Prioritized Action Plan (to reach minimum deploy readiness)

Small, ordered plan **without** writing or modifying code, tests, or config—only planning and docs.

1. **Document migration and data prerequisites (blocking)**  
   - In `docs/deploy.md` (or backend README / implementation_roadmap): state that for a new environment, (a) run `prisma migrate deploy` against the target database, and (b) run clue ingestion (or use a provided seed) so at least one full game can be played.  
   - Clarify whether migrations are run manually once, in a release job, or at app startup (and any tradeoffs).

2. **Add a short deploy/production runbook (blocking)**  
   - Single place that lists: required env vars for production (backend and frontend), CORS (FRONTEND_URL), and NEXT_PUBLIC_API_URL.  
   - Step order: apply migrations → run ingestion (or confirm seed) → set env → start backend → build and deploy frontend.  
   - Optional: one “sanity check” (e.g. open app, sign in, create game, start game, open one clue).

3. **Clarify test expectations for deploy (recommended)**  
   - Document which tests must pass before considering deploy (e.g. backend unit tests including game.service and auth).  
   - Document any known failing or environment-dependent tests (e.g. integration without DB, or specific frontend tests) and whether they are skipped in CI or accepted as “known failure” until fixed.  
   - Prevents deploy being blocked by non-critical test failures while keeping confidence in core behavior.

4. **(Optional) Minimal “first deploy” script or checklist**  
   - If desired: a shell script or documented commands that, given a DB URL and Supabase env, run migrations and ingestion so a new environment is playable.  
   - Improves repeatability; not strictly required if the runbook is clear.

5. **(Optional) Production env example**  
   - Copy of `.env.example` with production placeholders (e.g. `NEXT_PUBLIC_API_URL=https://api.yourdomain.com`) and comments that production must set these.  
   - Reduces risk of misconfiguration on first deploy.
