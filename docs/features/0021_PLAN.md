# Feature 0021: Deployment Infrastructure Alignment Validation

## Purpose

Confirm that the current project is aligned with the agreed deployment infrastructure plan (AWS, portfolio-quality, production-style). This is a validation and planning exercise only — no code, Terraform, CloudFormation, or scripts.

**Target architecture (locked):** Frontend: S3 + CloudFront (+ optional Route 53). Backend: ECS Fargate + ECR + ALB. Config/ops: SSM Parameter Store or Secrets Manager, CloudWatch Logs, basic CloudWatch Alarms. Database: Supabase (external).

---

## Alignment Summary

### What aligns

- **Backend runtime:** NestJS listens on `process.env.PORT ?? 3000`; single port, no hardcoded port. Compatible with ECS task definition and ALB target group (port configurable via PORT).
- **Backend env:** All configuration is env-based (DATABASE_URL, SUPABASE_*, FRONTEND_URL, PORT). No hardcoded secrets. Compatible with SSM Parameter Store or Secrets Manager via ECS task definition (env injection at runtime).
- **Backend build:** `npm run build` produces `dist/`; `npm run start:prod` runs `node dist/main`. Production run path exists; only the Dockerfile and deploy pipeline need to use it.
- **Frontend API usage:** All API calls go to an external backend via `NEXT_PUBLIC_API_URL`; no Next.js API routes (`app/api/` or `pages/api/`). No server-side backend proxy in the frontend app; compatible with static or server-hosted frontend.
- **Supabase:** Documented as external (`.env.example`, docs); backend uses DATABASE_URL and Supabase auth vars; frontend uses NEXT_PUBLIC_SUPABASE_* for client-side auth. No architectural conflict with target.
- **CORS:** Backend uses `FRONTEND_URL` for allowed origins; production can set FRONTEND_URL to CloudFront (or custom domain) origin. Aligns with ALB + CloudFront + S3 frontend.
- **Env documentation:** `.env.example` lists DATABASE_URL, SUPABASE_*, PORT, FRONTEND_URL, NEXT_PUBLIC_API_URL, NEXT_PUBLIC_SUPABASE_*. Matches what’s needed for deploy; SSM/Secrets Manager usage is an ops concern, not app code.

### What does not align (gaps)

- **Frontend static deployment (S3 + CloudFront):** Next.js is **not** configured for static export. `next.config.js` has no `output: 'export'`. Multiple pages use `export const dynamic = 'force-dynamic'` (e.g. `app/page.tsx`, `app/games/[id]/page.tsx`, `app/dashboard/page.tsx`, `app/auth/callback/page.tsx`). With the current build, Next.js produces a hybrid bundle that expects a Node server for those routes. **Pure S3 static hosting of build output is not supported as-is.** To align with “S3 for static Next.js / React build output,” the project needs either: (1) `output: 'export'` in next.config.js and validation that all routes (including dynamic `[id]`) are statically exportable and that no server-only features are used, or (2) a different target: run Next.js as a Node server (e.g. on ECS) behind CloudFront, with S3 only for static assets if desired — in that case the “S3 for static build output” wording in the target would need to be revised.
- **Backend Dockerfile:** The backend Dockerfile is **development-oriented**. It runs `npx prisma generate && npm run start:dev` (watch mode). For ECS/Fargate production, the image must build the app and run a production process (e.g. `npm run build && npm run start:prod` or equivalent). No production Dockerfile or production stage exists today.
- **Health check endpoint:** The backend has **no** `/health` (or similar) endpoint. ECS health checks and ALB target group health checks require an HTTP path that returns 2xx. Without it, ALB/ECS cannot mark the task healthy. This is a prerequisite for production deployment.
- **Frontend build-time env:** Next.js inlines `NEXT_PUBLIC_*` at **build** time. For a static S3/CloudFront deploy, the production build must be run with production values (e.g. NEXT_PUBLIC_API_URL pointing to the deployed backend). Documenting this is a prerequisite so deploy pipelines or runbooks set env at build time.

---

## Blocking Items

The following must be resolved before deployment using the locked target architecture.

1. **Frontend: Static export or architecture decision**
   - **Option A (align with “S3 for static build output”):** Add `output: 'export'` to Next.js config and ensure the app is fully statically exportable (no server-only features; dynamic routes like `games/[id]` handled via client-side navigation and client-side data fetching). Remove or replace `force-dynamic` where it prevents static export. Validate `next build` produces an `out/` directory suitable for upload to S3.
   - **Option B (keep current Next behavior):** Deploy the frontend as a Node server (e.g. Next.js on ECS behind CloudFront). Then the target doc must be updated to “Next.js on ECS (or similar) with CloudFront” rather than “S3 for static build output.” S3 can still be used for static assets if desired.
   - **Verdict:** Without one of these, the frontend is **not** deployable to “S3 for static Next.js / React build output” as stated in the locked target.

2. **Backend: Production Dockerfile (or production stage)**
   - The image used for ECS/Fargate must build the NestJS app and run a production command (e.g. `npm run build && node dist/main` or `npm run start:prod`), not `start:dev`. Add a production Dockerfile or a multi-stage Dockerfile with a production stage that installs deps, runs `prisma generate`, runs `nest build`, and runs `node dist/main` (or equivalent). Expose the same port (e.g. 3000) and rely on PORT env for override.

3. **Backend: Health check endpoint**
   - Add a minimal health check route (e.g. GET `/health` or GET `/`) that returns 200 and optionally a body like `{ "status": "ok" }`. No auth required. Document the path for ALB and ECS health check configuration. Without this, ECS and ALB cannot reliably determine task health.

4. **Deploy runbook and env at build time**
   - Document that frontend production build must be run with production `NEXT_PUBLIC_*` values (NEXT_PUBLIC_API_URL, NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY). Document migration and ingestion prerequisites (e.g. `prisma migrate deploy`, clue ingestion) per Feature 0020. No code change required; runbook or deploy checklist must exist so deployers set env and run steps in the correct order.

---

## Non-Blocking Improvements

- **Backend:** Add a `Dockerfile.prod` or multi-stage build in the same repo so both dev and prod images are explicit; document which image tag ECS uses.
- **Backend:** Consider a readiness probe (e.g. DB connectivity) in addition to a simple liveness `/health` if desired for stricter health semantics; not required for minimal ALB/ECS health.
- **Frontend:** If using static export, add a redirect or error document for SPA-style routing (e.g. CloudFront error pages → index.html for 404) so client-side routing works when users land on deep links.
- **Ops:** Document how secrets (DATABASE_URL, SUPABASE_JWT_SECRET) are loaded from SSM Parameter Store or Secrets Manager into the ECS task definition; no app code change needed.
- **Logging:** Ensure backend logs to stdout/stderr so CloudWatch Logs can capture them; NestJS Logger does this by default. Document log group and retention if desired.

## Architectural Mismatches or Risks

| Area | Risk or mismatch | Mitigation |
|------|------------------|------------|
| Frontend build output | Current Next.js build is not static; “S3 for static build” is not satisfied. | Implement Option A (static export) or Option B (Next on ECS) and update target doc. |
| Backend Dockerfile | Dev-only CMD; production run path not used in container. | Add production Dockerfile or stage (blocking). |
| Health checks | No HTTP endpoint for ALB/ECS. | Add `/health` (or equivalent) and document path (blocking). |
| Env at build time | NEXT_PUBLIC_* must be set when building frontend; easy to miss in CI/deploy. | Document in runbook and deploy checklist (blocking if missing). |
| Supabase | External dependency; availability and quotas are outside AWS. | Already documented; ensure runbook notes Supabase as external and any required Supabase project config (e.g. redirect URLs for production domain). |
| Port | Backend EXPOSE 3000 and default PORT 3000; ALB must target the same port the container listens on. | No mismatch; document that ECS task definition and ALB target group use the same port (e.g. 3000 or PORT). |

---

## Deployment Readiness Verdict

**Not ready to deploy as-is.**

**Reason:** Three blocking items prevent deployment against the locked target:

1. **Frontend** is not compatible with “S3 for static Next.js / React build output” without either enabling static export (and validating all routes) or changing the target to a Node-hosted Next.js (e.g. on ECS).
2. **Backend** container image is development-only; no production build or CMD for ECS/Fargate.
3. **Backend** has no health check endpoint for ALB/ECS.

**Ready to deploy with minor fixes:** Yes, **after** the blocking items above are addressed. The application logic, env model, CORS, and Supabase usage are compatible with the target. No alternative platforms or major re-architecture are required; the gaps are configuration (Next.js static export or target wording), a production Dockerfile (or stage), a health endpoint, and a clear deploy runbook.

**Summary:** Resolve the four blocking items (frontend static vs server decision and implementation, production Dockerfile, health endpoint, deploy runbook with build-time env and migration/ingestion steps). After that, the project is aligned with the agreed AWS deployment architecture and can be deployed with the intended infrastructure (S3 + CloudFront frontend, ECS Fargate backend, ALB, SSM/Secrets Manager, CloudWatch, Supabase external).
