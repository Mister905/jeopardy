# Feature 0018: Player Option to Pass on a Clue

## Description

Add an option for the player to pass on a clue instead of being forced to answer. In authentic Jeopardy, players may choose not to answer with no penalty. This feature aligns with real Jeopardy rules while preserving backend-authoritative scoring.

**Explicit UI requirement:** A new “Pass” button must be displayed immediately to the right of the existing “Show Answer” button. The Pass button must only be visible while a clue is active and unanswered. Visual placement must not disrupt existing button order or layout hierarchy.

**Constraints:** No new UI libraries. Backend remains authoritative; frontend emits intent, backend enforces outcome.

## UI Interaction Changes

1. **Pass button placement and visibility**
   - In `AnswerAdjudication`, in the same block where “Show Answer” is rendered (`!showAnswer`), add a “Pass” button immediately to the right of “Show Answer”.
   - Both buttons are visible only while the clue is active and unanswered (before “Show Answer” is clicked). After “Show Answer” is clicked, only “I got it right” / “I got it wrong” are shown; Pass is hidden.
   - Use existing layout (e.g. flex) so order is: [Show Answer] [Pass]. No new wrapper that would invert or disrupt the existing primary/secondary hierarchy (Show Answer remains the primary action).

2. **Pass action flow**
   - User clicks “Pass” → frontend calls pass API (e.g. `passClue(gameId, clueId)`).
   - Frontend does not reveal the answer. On success, backend marks clue resolved (or equivalent) with no score change; frontend refreshes game state and closes the clue modal (or shows resolved state and Close), consistent with current “clue resolved” behavior.

3. **Turn progression**
   - After a pass, turn progression continues as today: the clue is no longer selectable; the board remains in the same round until all clues are resolved. No extra “turn” entity; progression is “clue resolved → back to board → player selects next clue.”

---

## Backend Game State Transitions Affected by Pass

1. **Regular clue (non–Daily Double)**
   - Current: `UNANSWERED` → (answer with correct/incorrect) → `RESOLVED`, score delta ±value.
   - With pass: `UNANSWERED` → (pass) → `RESOLVED`, score delta 0. No `ANSWERED` state for regular clues.

2. **Daily Double**
   - **Pass is NOT available for Daily Double clues.** The Pass action must not be offered for Daily Doubles under any circumstance.
   - Current flow remains unchanged: `UNANSWERED` → (wager) → `ANSWERED` → (answer correct/incorrect) → `RESOLVED`. Daily Doubles require a wager and an answer submission to resolve; there is no pass path.
   - **Frontend:** Do not render the Pass button when the active clue is a Daily Double (neither on the intro screen nor on the question screen after wager).
   - **Backend:** Reject any attempt to pass a Daily Double with a validation error (e.g. 400 with a message such as “Pass is not allowed for Daily Double clues”).

3. **Final Jeopardy**
   - No pass. Player must wager (including $0) and then answer correct/incorrect. Pass button must not be shown in Final Jeopardy view. No backend change for Final Jeopardy.

4. **Already-resolved clues**
   - Pass is not available. Backend rejects pass for clue not in `UNANSWERED`. Frontend does not show Pass when `selectedClue.state === 'RESOLVED'` or when showing the post-answer resolved view.

---

## How a Passed Clue Is Marked

- **Option (recommended):** Keep existing `ClueState`: pass transitions the clue to `RESOLVED` with `scoreDelta = 0` and no “correct” answer recorded. Optionally add a `passed: boolean` on `GameClue` (or in response DTO only) so UI/analytics can distinguish “passed” from “answered wrong with value 0” (the latter cannot occur with current dollar values). If no DB schema change is desired, backend can infer “passed” when `state === RESOLVED`, `scoreDelta === 0`, and no `correct`/answer stored (if that fits current schema).
- **Alternative:** Add `PASSED` to `ClueState` and transition to `PASSED` instead of `RESOLVED` for pass. Round-completion logic must then treat `PASSED` like `RESOLVED` (clue is done). Response DTOs and frontend `ClueState` would include `PASSED`.
- Recommendation: **RESOLVED + scoreDelta 0 + optional `passed` flag** to avoid extra state and keep round-completion logic unchanged (“all clues RESOLVED” or “all clues RESOLVED or PASSED” if PASSED is introduced).

---

## Scoring Behavior When a Clue Is Passed

- Score does not change. Backend sets `scoreDelta = 0` and does not add or subtract from `game.score`.
- User stats: `updateUserStatsOnClueResolved` must not treat a passed clue as correct or incorrect. Either:
  - Do not call `updateUserStatsOnClueResolved` for pass, or
  - Call it with a third parameter (e.g. `passed: true`) and in `user.service` skip updating correct/incorrect counts and streaks for passed clues.

---

## Turn Progression After a Pass

- Same as after a normal answer: clue moves to `RESOLVED` (or `PASSED` if that state is added); modal closes or shows resolved view with Close; board re-renders with that clue marked done; player can select another clue. No change to “who’s turn” or round advancement beyond existing “all board clues resolved → Final Jeopardy eligibility” logic.

## Special Cases Summary

| Case | Pass allowed? | Behavior |
|------|----------------|----------|
| Regular clue, UNANSWERED | Yes | Pass → RESOLVED, scoreDelta 0. |
| Daily Double (any state) | **No** | Pass button must not be rendered. Backend must reject pass with validation error. Wager + answer required to resolve. |
| Final Jeopardy | No | Pass button not shown; no backend support. |
| Already-resolved clue | No | Backend returns 4xx if pass requested; frontend does not show Pass. |

---

## Daily Double Handling (Explicit Requirements)

- **The Pass action MUST NOT be available for Daily Double clues.**
- **Frontend:** The frontend must not render the Pass button when the active clue is a Daily Double (neither on the intro screen, nor on the wager screen, nor on the question screen after wager).
- **Backend:** The backend must reject any attempt to pass a Daily Double with a validation error (e.g. 400 and a message such as “Pass is not allowed for Daily Double clues”).
- **Resolution:** Daily Doubles require a wager and an answer submission to resolve; there is no pass path for them.

---

## API Contract Changes

1. **New endpoint (recommended):**  
   `POST /games/:id/clues/:clueId/pass`  
   - Auth: same as answer (authenticated, game owner).  
   - Response: same shape as answer (e.g. `gameClueId`, `clueId`, `state`, `scoreDelta: 0`, `newScore` (unchanged), `answeredAt`, optional `passed: true`). Optionally return full game DTO for client sync.

2. **Alternative:** Extend existing answer endpoint:  
   `POST /games/:id/clues/:clueId/answer`  
   - Body: `{ correct?: boolean, pass?: boolean }` with validation: exactly one of `correct` or `pass` must be true/present.  
   - If `pass === true`, backend performs pass logic (RESOLVED, scoreDelta 0), ignores `correct`.

3. **Idempotency / errors:**  
   - 400 if clue is not in a passable state (e.g. already RESOLVED).  
   - **400 with a validation error if the clue is a Daily Double** (e.g. “Pass is not allowed for Daily Double clues”).  
   - 404 if game or clue not found; 403 if not game owner. Same as current answer endpoint.

---

## Backend Authority Preserved

- Frontend sends a single intent: “pass this clue” (e.g. POST to pass endpoint or POST answer with `pass: true`).
- Backend: validates game state, clue state, and ownership; **rejects pass for Daily Double clues with a validation error**; allows pass only for regular clues in UNANSWERED; performs state transition and sets `scoreDelta = 0`; updates game score only if needed (no change for pass); persists and returns new state.
- Frontend does not compute score or state; it refetches game/board after pass (e.g. via existing `fetchGameData`) and updates UI from server response. Same pattern as `answerClue` today.

## Testing Considerations and Edge Cases

1. **Backend**
   - Pass on regular UNANSWERED clue → state RESOLVED, scoreDelta 0, score unchanged.
   - **Reject pass for Daily Double with validation error (400)** regardless of state (UNANSWERED or ANSWERED).
   - Reject pass when clue already RESOLVED.
   - Reject pass when game not ACTIVE.
   - Round completion: after pass, when all board clues are RESOLVED, transition to FINAL_PENDING or ELIMINATED same as today.
   - User stats: no increment of correct/incorrect and no streak update for passed clues.

2. **Frontend**
   - Pass button is visible only when clue is active and unanswered **and the clue is not a Daily Double** (regular clue only, before Show Answer).
   - **Pass button must not be rendered when the active clue is a Daily Double** (intro, wager, or question step).
   - Pass button is not visible in Final Jeopardy, after Show Answer, or for resolved clues.
   - Clicking Pass does not reveal the answer; modal closes or shows resolved view after success.
   - Layout: Pass is immediately to the right of Show Answer; existing button order and hierarchy unchanged.
   - Error handling: if pass API fails, show error and leave modal open; do not optimistically clear clue.

3. **Edge cases**
   - Double-submit: backend should reject second pass (clue already RESOLVED).
   - Network failure: frontend keeps modal open, shows error, allows retry or Close.
   - Concurrency: if two tabs answer and pass the same clue, backend accepts first and rejects second.
