# 0022: CI/CD Phase 1 (GitHub Actions)

## Description

Add minimal, production-realistic CI/CD for Trivia Master using GitHub Actions. Scope is intentionally small: no blue/green, canary, multi-env, Terraform, or GitOps. AWS resources (ECS cluster/service, ALB, ECR repo, S3 bucket, CloudFront distribution) are assumed to exist and are managed manually. Pipelines trigger on push to `main`; credentials come from GitHub Actions secrets. If any step fails, the workflow stops and later steps do not run—safe-by-default to prevent partial deployments.

---

## Backend (NestJS on ECS Fargate)

**Workflow (high-level):** On push to `main`, run backend tests, build a linux/amd64 Docker image, push to Amazon ECR, then trigger an ECS rolling deployment via `update-service --force-new-deployment`. No new AWS resources; reuse existing ECR repository and ECS cluster/service/task definition.

**Steps to implement:**

1. **Install dependencies** — `npm ci` in `backend/`.
2. **Run backend tests** — `npm run test` (and optionally `test:e2e` or `test:integration` if desired; user asked for “run backend tests”). If tests fail, the job stops; no image build, push, or ECS update runs.
3. **Build Docker image** — Use `backend/Dockerfile.prod`; build for `linux/amd64` (e.g. `docker build --platform linux/amd64 -f Dockerfile.prod -t <ECR_URI>:<TAG> .`). Image must be linux/amd64 for Fargate (see deploy.md). If build fails, no push or ECS update runs.
4. **Push to ECR** — Authenticate to ECR (e.g. `aws ecr get-login-password`), tag and push the image. Use a **deterministic tag** (e.g. short commit SHA: `git rev-parse --short HEAD`) so rollback can target a known good image; optionally also tag the same image as `:latest` for convenience. If push fails, ECS update does not run.
5. **Trigger ECS rolling deployment** — `aws ecs update-service --cluster trivia-master-backend-cluster --service trivia-master-backend-service --force-new-deployment --region us-east-1`. Task definition references the deterministic tag (or the tag the workflow pushed) so ECS runs that image; rollback re-deploys by updating to the previous deterministic tag.

**Credentials:** Use GitHub Actions secrets for AWS access (e.g. `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and optionally `AWS_REGION`). No `--profile admin` in CI; profile is for local CLI only. ECR repository URL and ECS cluster/service names can be secrets or repository variables.

**Rollback strategy (for deploy.md):**

- **Re-deploy previous image using the deterministic tag.** Rollback uses the deterministic tag (e.g. short commit SHA) to redeploy a known good image: update the ECS task definition to that tag and run `update-service --task-definition <family>:<revision> --force-new-deployment`, or re-run the workflow from the previous commit so that tag is pushed and ECS updated.
- **Verify rollback:** `curl -i https://<cloudfront-domain>/api/health` until 200 and `{"status":"ok"}`; check ECS service events and target health if needed.

**Files to add:**

- `.github/workflows/backend-deploy.yml` (or similar name). Content: one job that checks out repo, sets up Node (for npm ci/test), configures AWS credentials (e.g. `aws-actions/configure-aws-credentials`), runs the steps above. YAML outline: job on `push` to `main`; steps for checkout, npm ci, npm test, Docker build (with ECR login), docker push, aws ecs update-service.

**Relevant existing assets:**

- `docs/deploy.md` — Backend Deployment (build/push image, update-service); health check `GET /api/health` via CloudFront.
- `backend/Dockerfile.prod` — Multi-stage build; CMD `node dist/src/main.js`.
- `backend/package.json` — Scripts: `test`, `build`; no `deploy` script for backend.

## Frontend (Next.js static export → S3 + CloudFront)

**Workflow (high-level):** On push to `main`, build the Next.js static export, sync `out/` to the S3 bucket, then invalidate the CloudFront distribution. Rely on S3 versioning for rollback (restore previous object versions and re-invalidate).

**Steps to implement:**

1. **Install dependencies** — `npm ci` in `frontend/`.
2. **Build static export** — `npm run build`. Next.js is already configured for `output: 'export'` in production (`frontend/next.config.js`); build writes to `frontend/out/`. **Environment:** `NEXT_PUBLIC_*` variables are injected at **build time** from GitHub Actions secrets or repository variables; changing any of them requires a rebuild and redeploy. If the build fails, S3 sync and CloudFront invalidation do not run.
3. **Sync `out/` to S3** — `aws s3 sync frontend/out/ s3://<BUCKET>/ --delete`. Bucket name from secret or variable (e.g. `trivia-master-frontend`).
4. **Invalidate CloudFront** — `aws cloudfront create-invalidation --distribution-id <DIST_ID> --paths '/*'`. Distribution ID from secret or variable (e.g. `E3PQNFIR6EXJ2L`).

**S3 versioning:** Enable versioning on the frontend S3 bucket (one-time, Console or CLI) so rollback can restore previous object versions.

**Rollback strategy (for deploy.md):**

- **Restore previous S3 object versions** — Use S3 Console (Object versions) or CLI (`aws s3api list-object-versions`, then copy or restore prior versions) to restore the previous `out/` contents.
- **Re-invalidate CloudFront** — `aws cloudfront create-invalidation --distribution-id <DIST_ID> --paths '/*'` so edge caches serve the reverted content.

**Files to add:**

- `.github/workflows/frontend-deploy.yml`. One job on `push` to `main`: checkout, setup Node, npm ci, npm run build (from `frontend/`), configure AWS credentials, aws s3 sync, aws cloudfront create-invalidation. Build must have `NEXT_PUBLIC_*` set (e.g. from GitHub vars/secrets) for production.

**Relevant existing assets:**

- `docs/deploy.md` — Frontend Deployment (build, s3 sync, create-invalidation); bucket and distribution IDs.
- `frontend/package.json` — Scripts: `build`, `deploy` (build + s3 sync + invalidation; uses `CLOUDFRONT_DIST_ID`).
- `frontend/next.config.js` — `output: 'export'` in production.
