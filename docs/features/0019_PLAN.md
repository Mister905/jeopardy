# Feature 0019: Developer-Friendly Dockerized Setup

## Description

Create a **developer-friendly** dockerized environment that allows **one-command setup** and **consistent behavior across machines**. The project already uses **Supabase as a hosted external service** (Postgres database and Auth); Supabase is **not** dockerized and remains external. Docker is scoped to running only the **backend (NestJS)** and **frontend (Next.js)** in containers, with volume mounts and hot reload so developers can modify code locally and see changes immediately. The goal is reproducibility, minimal local setup (Docker and Docker Compose only), and clear developer ergonomics.

**Outcome:** One command (`docker compose up`) spins up backend and frontend; developers edit frontend/backend code on the host and see changes immediately; environment is reproducible across all machines. Data and auth stay on Supabase; no local database container.

---

## Architectural Intent

- **Supabase is external.** Postgres (database) and Auth live in Supabase’s hosted service. The backend connects to Supabase Postgres via `DATABASE_URL`; both backend and frontend use Supabase for authentication. No Postgres or database container is part of this feature.
- **Docker’s role.** Docker is a **developer experience and runtime consistency** tool: it runs backend and frontend in a predictable way so that “run this one command” works the same for every developer, without installing Node or managing local ports by hand.
- **What is in scope.** Backend service in Docker; frontend service in Docker with volume mounts and hot reload. Compose file defines these two services only. No `db` service; no local database.

---

## Relevant Files and Directories

### Files to Create

- **`docker-compose.yml`** (project root) — Define exactly two services: `backend`, `frontend`. One command (`docker compose up`) starts both. No database service.
- **`backend/Dockerfile`** — Image for the NestJS backend (development-oriented: watch mode, no heavy production-only layers).
- **`frontend/Dockerfile`** — Image for the Next.js frontend (supports volume mounts and hot reload in development).
- **`.env.example`** (project root) or **`docs/docker-setup.md`** — Document required environment variables for Docker and local use so developers know what to set; do not commit secrets.

### Files That May Need Changes

- **`backend/`** — No application code changes required; backend already reads `DATABASE_URL`, `PORT`, `FRONTEND_URL`, and Supabase-related env vars. Ensure port assignment in the compose setup does not conflict with the frontend (e.g. backend on 3001, frontend on 3000).
- **`frontend/`** — No application code changes required; frontend already uses `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_SUPABASE_*`. Compose and env documentation must make clear that `NEXT_PUBLIC_API_URL` is the URL the **browser** uses to reach the backend (e.g. `http://localhost:3001`).
- **`.gitignore`** — Keep `.env` and any `docker-compose.override.yml` (if used for local overrides) ignored; allow `.env.example` to be committed as a template.

---

## Service Layout and Ports

- **Two services only:** `backend`, `frontend`. No database service.
- **Ports:** Avoid conflicts. Suggested: **frontend** on host port `3000`, **backend** on host port `3001`. Document so developers open the app at `http://localhost:3000` and know the API is at `http://localhost:3001`.
- **Backend:** Listens on one port inside the container; that port is mapped to the host (e.g. 3001) so the browser and host tools can call it.
- **Frontend:** Exposes port 3000 on the host. Next.js dev server must bind to `0.0.0.0` (or equivalent) so it is reachable from the host.

---

## Environment Variables and Supabase

- **Handle environment variables and secrets appropriately.** No secrets in Dockerfiles or in the compose file; use env vars and a gitignored `.env`. Document required variables in `.env.example` or `docs/docker-setup.md`.
- **Supabase is external.** All Supabase configuration is provided via environment variables. No Supabase containers; backend and frontend talk to Supabase’s hosted URLs.
- **Backend:** Requires `DATABASE_URL` pointing to **Supabase’s Postgres** (connection string from Supabase project settings). Requires `PORT` (port the backend listens on inside the container), `FRONTEND_URL` (e.g. `http://localhost:3000` for CORS), and Supabase auth vars: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_JWT_SECRET`. Pass these via compose `environment` or `env_file`; do not hardcode.
- **Frontend:** Requires `NEXT_PUBLIC_API_URL` set to the URL the **browser** uses to reach the backend (e.g. `http://localhost:3001`). Requires `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (and any other `NEXT_PUBLIC_*` the app uses). These are used in the client; the value must be host-accessible where the browser runs, not a container hostname.
- **Reproducibility.** Document which env vars are required and how to obtain them (e.g. from Supabase dashboard). Same compose file and env contract for all developers so behavior is consistent.

---

## Backend in Docker

- **Purpose:** Run the NestJS API in a container so developers get a consistent runtime without installing Node locally.
- **Behavior:** Backend connects to **Supabase Postgres** via `DATABASE_URL`; no local database. Prisma migrations (if run at startup or as a documented step) target the same Supabase database.
- **Development ergonomics:** Default run should use watch mode so that mounting the backend source into the container allows code changes on the host to be picked up without rebuilding the image. Optimize the image for development (no heavy production-only layers).
- **Logs:** Backend stdout/stderr must remain visible (e.g. `docker compose logs backend`) for debugging.

---

## Frontend in Docker (Volume Mounts + Hot Reload)

- **Purpose:** Run the Next.js app in a container with **volume mounts for local code** and **hot reload enabled** so developers edit on the host and see changes immediately.
- **Volume mounts:** Mount the host `frontend` directory (or the relevant source/public subdirs) into the container so file changes on the host are visible inside the container. Strategy for `node_modules` (e.g. anonymous volume to use container’s copy) should avoid OS-specific native module issues while preserving hot reload.
- **Hot reload:** Next.js dev server must run in a mode that detects changes on the mounted volume (e.g. polling if needed in Docker). Dev server must bind so it is reachable from the host on the exposed port.
- **Optimization:** Image and default command should be tuned for fast startup and development; avoid heavy production build in the default dev flow.

---

## Logs and Debugging

- **Logs must be accessible.** Do not suppress or redirect backend or frontend output. Developers should be able to stream logs (e.g. `docker compose logs -f backend`, `docker compose logs -f frontend`) for debugging. Document this in README or docker-setup doc.

---

## Optional: docker-compose.override.yml

- **Optional:** A `docker-compose.override.yml` can provide dev-specific overrides (e.g. extra volume mounts, alternate env file). The base `docker-compose.yml` remains the minimal one-command stack so that `docker compose up` alone still works. Override can be gitignored if it contains machine-specific paths or secrets.

---

## Developer Flow (What Happens)

1. Developer runs `docker compose up` at project root.
2. Compose starts `backend` and `frontend` (no database service).
3. Backend starts; reads `DATABASE_URL` (Supabase Postgres) and Supabase auth vars; runs Nest in watch mode; logs to stdout.
4. Frontend starts; mounts local frontend code; runs Next dev server with hot reload; logs to stdout.
5. Developer opens `http://localhost:3000` in the browser; frontend loads; browser calls backend at `NEXT_PUBLIC_API_URL` (e.g. `http://localhost:3001`); CORS allows the origin per `FRONTEND_URL`.
6. Developer edits frontend or backend code on the host; volume reflects changes in the container; dev servers reload; developer sees changes without rebuilding images (except when dependencies change).

---

## Constraints

- No new product features; tooling and environment only.
- One command (`docker compose up`) starts the stack (backend + frontend only).
- No local database container; Supabase (Postgres + Auth) remains the external, hosted service.
- Backend runs in Docker; frontend runs in Docker with volume mounts and hot reload.
- Consistent behavior between developers; minimal local setup (Docker and Docker Compose).
- Docker images and default commands optimized for development speed, not production deployment.
